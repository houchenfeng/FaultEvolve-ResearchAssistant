# FaultEvolve：知识注入 + 树状进化 + 本地/云端混合的故障预测自演化系统

> 赛题：A 题「基于大模型 Agent 的器件故障预测算法及自动化调优」
> 版本：v0.1（设计稿）｜ 对标对象：百度伐谋（FAMOU / FM Agent, arXiv:2510.26144）
> 交付形态：一组 Agent Skill + 云端控制面 + 本地评估进程，宿主 Agent 首选 Codex

---

## 0. 一句话与设计目标

**FaultEvolve 是一个以 Skill 为入口的自演化算法系统**：宿主 Agent（Codex）通过 Skill 把「故障预测问题」整理成标准工件；云端负责知识注入和树状进化生成候选算法；本地评估进程在数据、仿真器或器材所在的机器上运行候选代码并打分。只有指标回传云端，数据与评估逻辑全程不出本地。

| 目标 | 具体要求 | 对应评审维度 |
|---|---|---|
| 复刻伐谋基础能力 | 任务工件（problem/evaluator/init/prompt）、冷启动、进化搜索、领域评估器、实验管理、诊断、结果可视化、混合云 | 自动化 |
| 创新 1：知识注入 | 从高被引论文、经典著作、互联网资料和专家方向中提炼「方案卡片」，驱动冷启动与变异 | 预测性能、泛化 |
| 创新 2：树状跨枝知识传播 | 用「解树」替代岛屿，把某个分支验证有效（或有害）的经验沿树传播给其他分支 | 预测性能、复杂性（Token） |
| 创新 3：新评估函数 | 稳健运维分 ROS：分层校验、机队加权、bootstrap 下分位、运维工作点召回、时间惩罚 | 预测性能、复杂性 |
| 创新 4：Jev 引导的树搜索 | 用结构化决策模型 Jev（TypeSafe AI）的校准概率分布作为树搜索的先验与快速评判：选节点、选算子、评估前预判候选价值、判断经验是否适用；并用真实评估结果持续校准和优化这个评判器 | 自动化（轮次/时间）、复杂性（Token 与本地算力） |
| 混合算力 | 云端生成 + 本地评估；本地可接仿真器或专用器材；排除大模型对测试集和评估的幻觉与作弊 | 泛化、可信 |

## 1. 对百度伐谋的拆解与映射

### 1.1 伐谋是什么（依据官方文档与论文）

**产品层（Famou Skills，开源于 `github.com/baidubce/skills`）**

| Skill | 职责 | 关键产物 |
|---|---|---|
| `famou-data-analysis` | 业务优先的数据理解与质量诊断 | 数据报告（嵌入 problem.md） |
| `famou-artifact-generator` | 端到端入口：澄清 → `problem.md` → 生成三件套 → 双候选区分度验证 | `problem.md` `evaluator.py` `init.py` `prompt.md` |
| `famou-experiment-manager` | 实验全生命周期（dry-run/提交/监控/暂停/继续/结果） | 排行榜、最优解、报告 |
| `famou-experiment-diagnosis` | 只读诊断：进展、多样性、评估器漏洞（reward hacking）、局部最优 | HEALTHY / WATCH / ABNORMAL / INCONCLUSIVE |
| `famou-result-visualization` | 最优解的交互式 HTML 可视化 | `famou_viz_result.html` |

- 评估器固定接口：`evaluate(path_user_py, task_name, timeout) -> {validity, combined_score, cost_time, error_info, metric}`。
- 混合云（Hybrid）：云端调度进化、调用大模型生成代码、维护种群和岛屿；本地常驻 `famou-ctl evaluator start` 进程，拉取候选代码、在本地评分并回传分数。数据和评估逻辑不离开本地；回传内容是 `evaluate()` 返回的全部字段，所以返回值里不能夹带敏感信息。

**算法层（FM Agent 论文）**

1. **冷启动**：多种生成 Agent 并行产出多样初始解，可加入专家指导（expert-in-the-loop）。
2. **进化**：按相似度聚类把初始解分到多个「岛屿」，各岛独立进化并周期性交流；采用基于聚类的自适应多样性采样（论文消融：比随机采样提升 58.26%，比 top-k 提升 10.99%），并保留精英池。
3. **领域评估器**：正确性、效果和大模型评审反馈相结合，支持多维指标（如精度与时延的权衡）。
4. **基础设施**：Ray 分布式；生成和评估两个工作池异步解耦。
5. **人机交互**：实时监控、自然语言干预、专家知识库检索增强（RAG）。

### 1.2 FaultEvolve 的保留、替换与新增

| 伐谋模块 | FaultEvolve 做法 | 变化 |
|---|---|---|
| artifact-generator + data-analysis | `fe-task-builder`：同样产出四件套，**格式与伐谋兼容**（同一个 `evaluator.py` 可直接提交伐谋） | 保留，额外输出 `knowledge_query.yaml` |
| 专家 RAG | `fe-knowledge-injector`：高被引文献、著作、网络资料与专家方向，经筛选提炼为**方案卡片**，并按实际效果学习卡片价值 | **新增/强化** |
| 岛屿模型 + 聚类采样 | **知识引导的树状进化（KGTE）**：解树 + Jev 引导的 PUCT 选择 + 跨枝知识传播 | **替换** |
| 精英池 | 精英集合 = 各分支前沿节点 + 全局帕累托前沿 | 改造 |
| 领域评估器 | **ROS 稳健运维分** + 三层校验 + 公开/私有双层评分 + 评估器自检 | **新增** |
| 大模型评审 | 可选附加反馈（可解释性、复杂度、风险），**不计入 combined_score** | 保留、降权 |
| experiment-manager | `fe-evolve-manager`：提交/监控/暂停/继续/调整/结果 | 保留 |
| experiment-diagnosis | `fe-diagnosis`：在伐谋四类结论基础上增加改进率后验、Jev 评判校准度和知识利用率 | 强化 |
| result-visualization | `fe-report`：进化树图、曲线、方案对比、session 导出（比赛交付物） | 强化 |
| Ray 异步 | 控制面异步任务队列；本地 worker 并发可配，按需接 Ray | 简化 |
| 混合云 Worker | `fe-local-evaluator`：拉取式 worker、沙箱执行、指标白名单、本地错例聚合分析 | 保留并加固 |

## 2. 总体架构

```
┌──────────────────────────── 宿主 Agent（Codex / 其它支持 Skill 的 Coding Agent）────────────────────────────┐
│  skills/                                                                                                      │
│   fe-task-builder   fe-knowledge-injector   fe-evolve-manager   fe-local-evaluator   fe-diagnosis   fe-report │
│   fe-fault-prediction-spec（领域规范：数据契约 / 标签构造 / 评测协议 / 错例→动作表）                          │
│        │ 调用 `fe` 命令行（src/faultevolve）                                                                  │
└────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────┘
         │ HTTPS（API Key）
┌────────▼─────────────── 云端控制面（Cloud Plane）───────────────┐        ┌──────── 本地执行面（Local Plane）────────┐
│ Experiment API     实验、配置、控制、人工指导                    │        │ Evaluator Worker（常驻，可多实例）        │
│ Evolution Engine   解树 / J-PUCT 选择 / 算子调度 / 终止判断       │  拉取  │  ├ 拉取候选代码（lease 租约）             │
│ Judge Service      Jev 快速评判（Choice/Score/Noul）+ 在线校准    │        │                                           │
│ Knowledge Service  文献检索 / 卡片库 / 向量索引 / 卡片效用        │◄──────►│  ├ 沙箱执行 evaluator.py（本地数据/仿真器）│
│ Insight Store      分支经验（正/负）/ 子树记忆 / 传播信誉          │  回传  │  ├ 指标白名单过滤后回传                    │
│ LLM Gateway        千问（Qwen）生成 / 缓存 / Token 记账          │  指标  │  └ 本地错例分析（只回传聚合统计）         │
│ Tree DB            节点、评估、事件（SQLite→PostgreSQL）          │        │ 私有数据 / 仿真器 / 器材 / 私有测试集     │
└──────────────────────────────────────────────────────────────────┘        └───────────────────────────────────────────┘
```

**边界原则**

1. 云端**看不到**：原始数据、标签、评估器源码（混合模式下）、私有测试集。
2. 本地**不做**：大模型推理和文献检索（避免在受限环境里装大量依赖）。
3. 云端只能拿到：`validity`、`combined_score`、白名单内的 `metric`、截断并脱敏后的 `error_info`、聚合后的错例统计（例如按厂商统计的漏告率）。
4. 分数**只由本地评估器产生**。大模型无法「声称」自己的方案达到了某个分数，从机制上排除幻觉。

## 3. Skill 体系设计

所有 Skill 放在 `skill/<name>/`（比赛模板要求），每个目录包含 `SKILL.md`、`scripts/`、`references/`。安装到 Codex 时复制或软链接到 Codex 的 skills 目录（以所用 Codex 版本文档为准，例如用户级 `~/.codex/skills/` 或仓库级 skills 目录）。

### 3.1 Skill 清单

| Skill | 触发场景 | 输入 | 输出 | 主要命令 |
|---|---|---|---|---|
| `fe-task-builder` | 用户要做故障预测或调优任务、生成工件、修评估器 | 数据目录、业务描述 | `problem.md` `evaluator.py` `init.py` `prompt.md` `config.yaml` | `fe task scan / validate / dual-check` |
| `fe-knowledge-injector` | 冷启动前；进化停滞时；用户给出专家方向时 | `problem.md`、`expert.md`（可选） | `knowledge/cards.jsonl`、`knowledge/report.md` | `fe knowledge build / add-expert / show` |
| `fe-evolve-manager` | 提交、监控、调整、继续、取消实验 | 工件目录、`evolve.yaml` | 实验 ID、进度、排行榜、最优解 | `fe evolve submit / status / update / pause / resume / continue / results` |
| `fe-local-evaluator` | 启动、恢复、巡检本地评估进程 | 实验 ID、`evaluator.py` | 常驻 worker、`.fe/eval_trace` | `fe worker start / status / stop` |
| `fe-diagnosis` | 「还健康吗 / 是否停滞 / 是否钻评估器空子」 | 实验 ID、本地工件 | 结论 + 证据 + 建议（只读） | `fe diagnose` |
| `fe-report` | 实验结束、整理交付物 | 实验 ID | 报告、进化树 HTML、对比表、session JSON | `fe report build / sessions` |
| `fe-fault-prediction-spec` | 被其它 Skill 引用（参考资料型） | — | 数据契约、标签构造、评测协议、错例→动作表 | — |

### 3.2 Skill 协作流程

```
用户：「用 FaultEvolve 优化 benchmark/hdd_mvp 的硬盘故障预测，目标 ROS ≥ 32，最多 50 轮」
  → fe-task-builder     扫描 → 澄清（一次只问一个问题）→ problem.md → 四件套 → 双候选验证
  → fe-knowledge-injector  根据 problem.md 生成检索式 → 检索与筛选 → 方案卡片（附来源）→ 用户确认或补充专家方向
  → fe-evolve-manager   dry-run（估算 Token 与时长）→ 用户确认 → 提交（只上传 problem/prompt/init/cards/config）
  → fe-local-evaluator  本地启动 worker（推荐用户手动在 tmux 或 nohup 中启动）→ 巡检
  → fe-evolve-manager   定期汇报：轮次、最优分、相对初始提升、有效率、近期改进率、Jev 校准度
       ↘ fe-diagnosis（按需，只读）
  → fe-report           Top-K 在私有测试集复评（本地）→ 报告 + 进化树 + session 导出
```

### 3.3 `SKILL.md` 写法约定（以 fe-evolve-manager 为例）

```markdown
---
name: fe-evolve-manager
description: 提交并管理 FaultEvolve 云端进化实验（混合模式：云端生成、本地评估）。当用户要运行、
  监控、暂停、继续、调整或获取进化结果时使用。实验必须先通过 fe-task-builder 的本地验证。
---
## 前置检查
1. `fe doctor`：CLI 版本、API Key、云端连通性
2. 工件目录必须包含 problem.md / evaluator.py / init.py / prompt.md / config.yaml，且 `fe task validate` 通过
## 提交
1. `fe evolve submit --dry-run --json` → 向用户展示预计 Token、轮次、上传清单（不含数据与 evaluator）
2. 用户确认后 `fe evolve submit -y --json`，记录 experiment_id
3. 转交 fe-local-evaluator 启动 worker；未收到 worker 心跳前不要报告“运行中”
## 监控
- `fe evolve status --json` 每 30 秒一次，直到 2 轮完成；之后按用户要求的频率汇报
## 禁止
- 不得在未确认的情况下取消、删除、重提实验
- 不得读取 data/holdout* 或把私有测试分数写入 prompt
```

## 5. 知识注入（创新 1）

### 5.1 知识来源与可信度

| 来源 | 获取方式 | 可信度信号 | 用途 |
|---|---|---|---|
| 高被引论文 | OpenAlex / Semantic Scholar / arXiv API | 引用数、**按发表年份归一化的引用百分位**、会议/期刊等级 | 方法类卡片（特征、模型、不平衡、迁移） |
| 经典著作与综述 | 人工书单 + 文献 API 元数据 | 引用数、再版次数 | 原理类卡片（可靠性工程、生存分析、极值理论） |
| 互联网资料 | 网络搜索（技术博客、厂商 SMART 白皮书、竞赛方案） | 来源域名白名单、多源交叉印证 | 工程技巧卡片（Backblaze 经验、竞赛 Top 方案） |
| 专家方向 | `expert.md`（自然语言）、运行中的 `guidance` 接口 | 人工赋予的优先级 | 高先验卡片、约束 |
| 内部经验（后验） | 进化中产生的 insight | 实测 Δ 分数与显著性 | 见第 6.8 节 |

### 5.2 注入流水线

```
problem.md ──► ① 检索式生成（大模型：问题类型 × 数据形态 × 难点 → 8~15 条查询）
          ──► ② 多源检索（每条取前 N，合并去重，保留 DOI 或 URL）
          ──► ③ 质量筛选：引用百分位 ≥ P70，或专家、白名单来源；近 3 年的论文放宽门槛
          ──► ③' 相关性初筛：Jev Score（5 级）批量判断「标题 + 摘要」与 problem.md 的相关度，只保留前 40%（快且便宜）
          ──► ④ 卡片提炼（千问只依据摘要或正文片段，必须引用原文句子作为证据）
          ──► ⑤ 适用性打分：Jev Score 对照 problem.md 的数据字段、约束、指标，取概率加权分作为卡片先验
          ──► ⑥ 聚类去重，形成「方向簇」（例如 时序趋势 / 厂商分治 / 生存分析 / 异常检测 / 集成）
          ──► ⑦ 输出 cards.jsonl + report.md，交用户确认或补充专家方向
```

**方案卡片 schema**

```json
{
  "id": "card-017",
  "title": "Using SMART attribute trends with gradient boosting for disk failure prediction",
  "source": {"type": "paper", "doi": "10.xxxx/xxxx", "url": "...", "year": 2021, "venue": "...", "citations": 312, "citation_pct": 0.93},
  "idea": "对关键 SMART 计数（5/187/197/198）在观测窗内计算差分、斜率和首次非零时间，再用 GBDT 建模",
  "evidence": "原文摘录句……",
  "applicability": {"score": 0.86, "requires": ["daily history >= 7 days"], "conflicts": []},
  "impl_hint": "groupby(serial).agg(last, first, max, slope)；缺失厂商属性以 NaN 保留，交给树模型处理",
  "expected_effect": "召回提升，误告率基本不变",
  "risk": "特征数膨胀带来时延上升；厂商间属性语义不一致",
  "tags": ["feature:trend", "model:gbdt"],
  "prior": 0.7
}
```

### 5.3 注入点

1. **冷启动**：每个方向簇选一张最高先验的卡片，生成一个种子解，每个种子成为一个主分支。这相当于伐谋的「多智能体并行冷启动」，但多样性来自知识而非随机。
2. **知识变异算子**：扩展节点时按 Thompson 采样抽一张卡片，要求大模型把它落地到父代码上。
3. **停滞触发**：当某分支连续多次扩展都没有显著提升（改进率后验上界低于阈值）时，触发一次**定向检索**，用该分支的错例画像生成新查询，补充新卡片。
4. **专家实时指导**：用户在运行中给出自然语言方向，立即转成高先验卡片并广播到全部分支。

### 5.4 知识价值学习与防幻觉

- 每张卡片维护 Beta(α, β)：由该卡片生成的子节点若显著超过父节点（Δ > δ），α+1，否则 β+1。后续抽卡时使用后验值，**让实测结果修正文献先验**。
- 卡片必须带可解析的 DOI 或 URL；检索阶段校验元数据（标题、年份、引用数）来自 API 而非大模型；无来源的卡片只能标记为 `llm_hypothesis`，先验减半。
- 报告中统计知识利用率：卡片被使用次数、成功率、贡献了最终最优解谱系的卡片列表（可解释性证据）。

## 6. 知识引导的树状进化 KGTE（创新 2 + 创新 4）

### 6.1 为什么用树而不是岛屿

岛屿模型用「隔离 + 周期迁移」维持多样性，但迁移的是**整段代码**，信息粒度粗，而且迁移时机固定。解树天然记录了**每一次修改的因果链**（父 → 子，附变更意图与 Δ 分数）。这让我们能以「经验」而不是「个体」为单位在分支之间传播知识：更细粒度、更省 Token，也更可解释。

### 6.2 解树结构

- **节点**：一个完整可运行的候选程序及其评估结果。
- **边**：一次算子操作，附 `operator`、`intent`（变更意图）、使用的卡片和 insight、Δ 分数。
- **分支**：以冷启动种子为根的子树（相当于岛屿，但允许跨枝交叉产生「多父节点」，严格说是 DAG）。
- **前沿**：每个分支中尚可扩展的节点（未达子节点上限，也未被剪枝）。

### 6.3 Jev：System One 快速评判器

[Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)（TypeSafe AI，2026 年 9 月发布）是「System One」结构化决策模型。它不生成文本，只对给定的 `state` 回答预先定义的类型化问题，每个答案都附带校准过的概率分布：

| 问题类型 | 输出 | 典型延迟与成本 |
|---|---|---|
| Choice | 从 ≤255 个选项中选一个，返回每个选项的概率与置信度 | 70~500 毫秒；成本约为通用大模型的 1/400 |
| Score | 在 2~10 个有序等级上打分，返回概率加权分数与完整分布 | 同上 |
| Noul | 是非判断，返回「是」的概率 | 同上 |

接口：`POST https://api.typesafe.ai/v1/systemone`，请求体包含 `model`（`jev-latest` 或固定版本号）、`state`（字符串、对象或数组，≤64k tokens）和 `questions`（多个问题一次往返并行回答）。

**分工原则**：千问（System Two，慢思考）负责生成代码、抽取经验、写摘要；Jev（System One，快决策）负责进化中所有**高频、低复杂度、需要概率的判断**；本地评估器负责**真实分数**。三者职责不重叠：Jev 的输出只是先验，永远不能替代评估器的分数，因此不会引入「大模型声称分数」式的幻觉。

**Jev 在系统中的决策点**

| 决策点 | 问题类型 | state（均为云端已有信息，不含原始数据） | 用途 |
|---|---|---|---|
| 扩展哪个节点 | Choice：兄弟节点 +「扩展当前节点」 | 实验目标、全局最优、各候选节点摘要（分数、分项指标、变更意图、分支记忆） | J-PUCT 先验 \(P_{jev}\) |
| 用哪个算子 | Choice：6 个算子 | 节点摘要 + 错例画像 + 分支记忆 | 与算子 Thompson 采样融合 |
| 新候选值不值得评估 | Score（5 级）+ Noul | 父节点摘要 + 变更意图 + 代码 diff | 评估前预判；调度本地算力 |
| 候选是否违反约束或泄漏 | Noul | 代码 diff + 硬约束清单 | 预筛；高风险候选抽样复核 |
| 外枝经验或知识卡片是否适用 | Noul | 经验或卡片 + 目标节点摘要 | 跨枝传播与抽卡的适用性概率 |
| 文献是否与任务相关 | Score（5 级） | 论文标题与摘要 + problem.md 摘要 | 知识注入的批量初筛 |
| 是否值得继续进化 | Noul | 最近 W 轮轨迹摘要 | 停止判断（与统计量联合） |

Score（5 级）的等级定义示例：`["明显变差：ROS 降低 >2", "略差：降低 0.5~2", "持平：±0.5 以内", "略好：提升 0.5~2", "明显更好：提升 >2"]`。等级描述会在 6.6 节中随真实结果自动修订。

### 6.4 选择策略：Jev 引导的 PUCT（J-PUCT）

采用 AlphaZero 式的 PUCT 自根向下选择：在每个内部节点比较「扩展自己」与「进入某个子节点」，Jev 提供策略先验，真实评估提供价值。

\[ U(c) = Q(c) + c_{puct}\cdot \tilde P(c)\cdot\frac{\sqrt{N_{parent}}}{1 + N_c} - \lambda_{dup}\cdot dup_c \]

- **价值 Q(c)（最大值回传）**：优化任务关心「能否刷新最优」而非平均分，所以回传子树内的最好成绩：
  \[ Q(c) = \frac{\big(\max_{d\in \mathrm{subtree}(c)} s_d - s_{parent} - \delta\big)_+}{s^* - s_{init} + \epsilon} \]
  其中 \( \delta = \kappa\cdot\sigma_{noise} \)，\( \sigma_{noise} \) 由评估器返回的 bootstrap 标准差换算，**落在噪声内的提升不计入价值**。
- **先验 \(\tilde P(c)\)**：Jev Choice 的概率与均匀分布按信任度混合：
  \[ \tilde P(c) = \tau\cdot P_{jev}(c) + (1-\tau)\cdot\frac{1}{|\mathrm{children}|+1} \]
  信任度 τ 来自 6.6 节的在线校准；Jev 判断不准时 τ 自动下降，搜索退化为标准 UCT。
- **渐进展宽**：节点最多子节点数 \( K_n = \lceil C\cdot N_n^{\alpha} \rceil \)（α≈0.5）；未达上限时「扩展当前节点」作为一个选项参与比较。
- **批量并行**：多个 worker 同时空闲时使用虚拟损失（virtual loss），避免重复选中同一节点。

### 6.5 评估前预判与本地算力调度

混合模式下，本地评估往往是最贵、最慢的环节（仿真器或器材可能每次运行数十分钟甚至数小时，且无法扩容）。因此每个新候选入队前先由 Jev 预判：

- 期望改进 \( \mathbb{E}_{jev}[\Delta] = \sum_k p_k v_k \)（v_k 为各等级的中点），提升概率 \( P_{jev}(\uparrow) = p_{略好} + p_{明显更好} \)；
- 违规概率 \( P_{jev}(\text{violation}) \)（Noul）。

**队列策略**：按 \( P_{jev}(\uparrow) \) 降序排队；若 \( P_{jev}(\uparrow) < \theta_{low} \) 且 \( P_{jev}(\text{violation}) > 0.8 \)，则暂缓评估。为防止评判器的偏差自我强化，**被暂缓的候选按 10% 比例随机抽取做真实评估**，这些结果专门用于校准。

### 6.6 评判器的在线校准与自我优化

这一节回答「怎样用树搜索和 Jev 的概率分布来评判、并优化评估函数」：搜索时使用的**评判函数**本身也在被评估和进化。

1. **校准度量**：每个候选得到真实分数后，把 Δ 落入的等级作为真实标签，与 Jev 的预测分布比较。按决策类型、算子和分支维护滑动窗口的 Brier 分数与 ECE（期望校准误差）。
2. **信任度**：
   \[ \tau = \mathrm{clip}\Big(1 - \frac{\mathrm{Brier}_{jev}}{\mathrm{Brier}_{base}},\ 0,\ 1\Big) \]
   其中 \( \mathrm{Brier}_{base} \) 是直接用历史等级频率预测的基线。Jev 不比基线好时 τ→0。
3. **概率再校准**：对每类决策做温度缩放或 Platt 缩放，把 Jev 的原始概率映射为本任务上的校准概率。
4. **评判问题的自我优化**：当某类决策的 ECE 持续偏高时，由千问根据最近的真实案例改写该 Jev 问题的 `instructions` 和等级描述（例如把「略好」具体化为「ROS 提升 0.5~2，典型变更如加入 7 日差分特征」），生成新版本。新旧版本在最近 N 条已知结果上**离线回放**比较 Brier 分数，新版本更好才上线。问题版本号写入 `evolve.yaml` 和事件日志，保证可复现。
5. **搜索用价值函数**：候选评估前使用 \( \mathbb{E}_{jev}[\Delta] \)，评估后使用真实 ROS；对外报告永远只用真实 ROS（见 7.5 节）。

### 6.7 变异算子（均由大模型执行，云端生成）

| 算子 | 输入上下文 | 目的 | 触发偏好 |
|---|---|---|---|
| `refine` 错例驱动微调 | 父代码 + 指标 + 本地聚合错例画像 | 针对误告或漏告局部改进 | 高分节点 |
| `inject` 知识变异 | 父代码 + 一张卡片 | 引入新方法 | 中高分、卡片未用过 |
| `crossover` 跨枝交叉 | 两个互补父代（一个高召回、一个低误告） | 合并优势 | 分支间行为差异大时 |
| `transplant` 经验移植 | 父代码 + 外枝 insight | 跨枝知识传播 | 有高信誉的外枝 insight |
| `diversify` 新开分支 | 未覆盖的方向簇卡片 | 保持多样性 | 全局近期改进率下降时 |
| `simplify` 精简 | 高分节点 | 降时延、降复杂度（复杂性维度） | 前沿节点，分数不降即接受 |

算子选择：每个分支对每个算子维护 Beta 成功率（成功 = 子节点 > 父节点 + δ）。选择时把 Thompson 采样值与 Jev 的算子 Choice 概率按信任度 τ 加权融合，并对每种算子设最低探索配额。

### 6.8 树状跨枝知识传播

**(a) 经验（insight）抽取**：每次评估完成后，若 |Δ| > δ（显著）：
- 由大模型对比父子代码 diff 与指标变化，生成 insight：`变更摘要`、`机制假设`（为什么有效或有害）、`适用条件`、`tags`；
- Δ > δ 记为正经验，Δ < −δ 记为**负经验**（避免其他分支重复踩坑），并记录 z = Δ/σ_noise。

**(b) 自底向上汇总（子树记忆）**：insight 沿父链上传。每个内部节点维护 `branch_memory`，即其子树中按 z 排序的前 k 条经验。只在分支根和高访问节点上每隔 K 次更新调用一次大模型做摘要，控制 Token。

**(c) 横向传播（跨枝）**：扩展分支 B 中的节点 m 时，从其它分支检索 insight，打分：
\[ r_i = z_i \cdot \mathrm{app}(i, m) \cdot \mathbb{E}[\mathrm{Beta}(\alpha_i,\beta_i)] \cdot \mathrm{novelty}(i, \mathrm{lineage}(m)) \]
- `app`：经验对 m 的适用概率。先用 tags 与代码嵌入的相似度粗筛出前 20 条，再对每条向 Jev 提一个 Noul 问题（「该经验能否直接用于这个方案？」），取校准后的概率。这样能识别技术栈差异，例如对树模型有效的特征技巧，对规则方案未必有效；
- `novelty`：m 的祖先链中尚未包含该经验；
- 取前 k 条放入 prompt 的「其他分支已验证经验」和「其他分支已证伪做法」两个段落，或直接作为 `transplant` 算子的输入。

**(d) 传播验证与信誉**：经验被移植后，若接收节点显著提升，则 α+1，否则 β+1。信誉低的经验逐渐淡出；在 ≥ 3 个分支上都有效的经验升级为**全局规律**，写入 `fe-fault-prediction-spec` 的错例→动作表。这就是比赛要求的「将调优过程沉淀为标准化规范/Skill」的自动化来源。

**(e) 与岛屿迁移的区别**：迁移的单位是**可复用、带条件的经验**而非整段代码；传播时机由显著性触发而非固定周期；负经验也会传播。

### 6.9 多样性与剪枝

- **行为指纹**：本地 worker 回传聚合指标向量（按厂商统计的召回与误告率、分数分位点），作为无泄漏的「行为嵌入」；与代码嵌入拼接后用于去重和选择交叉对象。
- **剪枝**：连续 L 次扩展无显著提升、且 Jev 预判的提升概率持续低于阈值的节点冻结；分支整体改进率低于阈值时停止分配预算，但保留其经验。

### 6.10 停止条件（自动化维度）

满足任一即停止：
1. 达到目标分数；
2. 预算（轮次、Token、墙钟时间）耗尽；
3. **改进停滞**：最近 W 次扩展的显著改进率 Beta 后验的 90% 上界 < ε，且 Jev 的「是否值得继续」Noul 概率 < 0.2（两者同时满足，避免单一信号误判）。

报告中给出「达到目标所需轮次」和停止原因。

### 6.11 单轮流程（异步流水线）

```
选择(J-PUCT：Jev Choice 先验 + 最大值回传) → 选算子(Thompson ⊕ Jev Choice)
 → 组装上下文(父代码 + 指标 + 错例画像 + 卡片 + 外枝经验[Jev 适用性] + 负经验)
 → 千问生成（LLM Gateway 记 Token）→ 静态检查（语法、禁用 API）
 → Jev 预判（Score 期望改进 + Noul 违规概率）→ 按提升概率排队（10% 随机复核）
 → 本地 worker 拉取并评估 → 回传白名单指标
 → 更新树与 Q 值；更新算子、卡片、经验的 Beta；更新 Jev 校准与信任度 τ
 → 抽取 insight → 子树记忆上传 → 检查停止条件
```

生成池与评估池解耦：云端可同时挂起多个候选，本地多个 worker 并发评估（`--max-concurrent`）。

## 7. 评估体系（创新 3）

### 7.1 三层结构

1. **硬约束层**（任一失败则 validity=0）：程序正常退出且不超时；输出格式、覆盖率、取值合法；**防泄漏**：候选只能看到临时副本里的公开文件；静态规则禁止路径回溯、目录遍历、读取工作目录、子进程和网络；标签文件永不进入候选可见目录。
2. **指标层**：按机队加权的混淆矩阵（每个负样本代表约 10 块健康盘）、precision/recall/F1、误告率、漏告率、AUPRC、R@FAR、运行时间。
3. **稳健聚合层**：bootstrap 下分位、运维工作点、时间惩罚，最终合成 `combined_score`。

### 7.2 稳健运维分（Robust Operational Score, ROS）

\[ \mathrm{ROS} = 100\cdot\big(0.5\,F1_{p10} + 0.3\,\mathrm{AUPRC} + 0.2\,R@\mathrm{FAR}_{\le 0.2\%}\big)\cdot\min\!\big(1, \tfrac{T_{budget}}{t}\big) \]

| 组成 | 含义 | 设计动机 |
|---|---|---|
| \(F1_{p10}\) | 200 次分层 bootstrap 下加权 F1 的 10% 分位 | 比赛主指标是 F1；取下分位惩罚「在噪声上碰巧选中好阈值」 |
| AUPRC | 分数排序质量（加权） | 与阈值无关，提供平滑、可区分的进化信号 |
| R@FAR | 误告率 ≤ 0.2% 时的最大召回 | 贴近运维真实约束：误告预算固定，看能抓住多少坏盘 |
| 时间因子 | 超过 600 秒按比例扣分 | 纳入复杂性维度，防止靠堆算力刷分 |

**实测区分度**（验证集）：规则基线 12.94；逻辑回归初始解 22.81；LightGBM 趋势特征参考方案 33.70（私有测试集 33.58，与验证集一致）。评估器能单调地区分三档质量，且留有充足的进化空间。

**通用形式**（迁移到内存、光放大器时可配置）：
\[ \mathrm{ROS} = 100\cdot\Big(\sum_k w_k\,\mathrm{LCB}_{q}(m_k)\Big)\cdot\prod_j \phi_j(c_j) \]
其中 m_k 为质量指标（F1、AUPRC、R@FAR、提前量得分等），LCB_q 为 bootstrap 下分位；\( \phi_j \) 为成本因子（时延、模型大小、特征数），权重写在 `problem.md` 中。

### 7.3 公开集与私有集双层评分

- 进化过程只使用**验证集（val）**打分；私有**测试集（test）**只在本地、只在最终裁决时使用，分数不回传云端、不写入 prompt。
- 报告同时给出 val/test 分数和二者之差（泛化间隙）。间隙过大说明对验证集过拟合，会被 `fe-diagnosis` 标记为 WATCH。
- 训练、验证、测试严格按时间外推（2024Q3 → 2024Q4 → 2025Q1），每块盘在每个划分中只出现一次，且历史在各自的 cutoff 截止，「盘消失」无法泄露标签。

### 7.4 评估器自检（沿用并加强伐谋规范）

1. **双候选区分度**：两个质量不同的候选分数方向正确（已实现，见 `tests/`）。
2. **对抗探针**：读标签、路径回溯、输出不全等作弊候选必须得 0 分（已实现）。
3. **随机分数探针**：随机分数方案的 AUPRC 应接近故障率，R@FAR 应接近 0。
4. **复现检查**：`fe-diagnosis` 在本地隔离目录中复跑 Top-K，比较平台分与复现分。

### 7.5 报告分与选择分分离

`combined_score`（ROS）是**唯一对外报告**、也用于与伐谋对比的分数。进化内部的选择信号（Jev 先验与预判、噪声阈值 δ、多样性惩罚）只影响「下一步扩展谁、先评估谁」，不改变任何节点的分数，保证与伐谋的比较口径完全一致。

| `POST /v1/workers/{id}/heartbeat` | 心跳（默认 30 秒）；超过心跳等待时长则暂停调度 |
| `GET /v1/jobs/next?experiment_id=&worker_id=` | 领取候选（附租约 `lease_until`；超时未回传则重新入队） |
| `POST /v1/jobs/{job_id}/result` | 回传结果（幂等；只接受白名单字段） |
| `GET /v1/experiments/{id}/status /leaderboard /tree /insights /events` | 监控与诊断（只读） |
| `POST /v1/experiments/{id}/control` | pause / resume / continue / cancel / update（先 dry-run） |
| `POST /v1/experiments/{id}/guidance` | 专家自然语言指导，转为高先验卡片 |

### 8.3 数据不出域与安全

- `.fe/metric_whitelist.yaml` 定义可回传的指标键；worker 在回传前过滤，`error_info` 截断到 500 字符并脱敏（去掉路径和序列号模式）。
- 候选代码在隔离环境中执行：独立虚拟环境或容器、无网络、只读挂载公开数据副本、限制 CPU、内存和时间。MVP 阶段用「临时副本 + 静态规则 + 超时」，正式版用容器。
- API Key 只存在环境变量或本地配置中，不进 Git。

### 8.4 部署形态

| 形态 | 云端 | 本地 | 适用 |
|---|---|---|---|
| 本地开发 | 同机进程（FastAPI + SQLite） | 同机 worker 进程 | 单元测试与调试，协议与正式版一致 |
| **标准混合（MVP 起即采用）** | 团队云服务器（控制面 + LLM Gateway + Judge Service） | 数据所在机器上的 1~N 个 worker | 硬盘 MVP、内存验证 |
| 器材在环 | 同上 | 连接仿真器或器材的工控机 worker，能力标签 `simulator:*` | 光放大器等内部数据迁移验证 |

## 9. 宿主 Agent：Codex

- **安装**：把 `skill/*` 放入 Codex 的 skills 目录，并在环境中 `pip install -e .` 安装 `fe` CLI。
- **角色**：Codex 负责「理解意图 → 调用 Skill → 运行 `fe` 命令 → 向用户解释」，相当于伐谋 Skills 中的 Coding Agent（DuMate、Comate 等）。
- **生成后端**：千问（Qwen），通过阿里云百炼 DashScope 的 OpenAI 兼容接口调用；LLM Gateway 保留切换其它模型的配置项。
- **评判后端**：Jev（`jev-latest`，生产中固定版本号以保证可复现），API Key 放在云端环境变量 `TYPESAFE_API_KEY`。
- **会话留痕**：`fe report sessions` 把 Codex 会话日志和云端事件合并，导出为比赛模板要求的 `sessions/*.json`。
- **自动化覆盖率**：统计全流程中需要人工确认的步骤（提交确认、启动 worker、专家方向），其余均由 Skill 自动完成。

## 10. 与评审维度的对应及实验设计

| 评审维度 | 证据 | 实验 |
|---|---|---|
| 预测性能 | 私有测试集 ROS、F1、误告率、漏告率 | FaultEvolve vs 伐谋 vs 初始解 vs 人工参考 |
| 复杂性 | 最优解运行时间、特征数、模型大小；每轮 Token；每单位提升的 Token | `simplify` 算子开/关 |
| 自动化 | 人工介入次数；达到目标分所需轮次和时间；本地评估次数 | J-PUCT vs UCT（去掉 Jev）vs 贪心 top-k；Jev 预判开/关 |
| 泛化 | 同一套 Skill 用于硬盘、内存、光放大器；val/test 间隙 | 跨数据集复用，只写数据适配器 |

**消融实验**：① 去掉知识注入（只用 init 冷启动）；② 去掉跨枝传播；③ 去掉负经验；④ 选择策略换成 UCT 或 top-k；⑤ 评估函数换成原始 F1（观察过拟合与 val/test 间隙）。每组 3 个随机种子，报告均值 ± 标准误。

## 12. 实施路线（按依赖顺序）

1. **基准与评估器**（已完成）：硬盘数据集、ROS 评估器、初始解、伐谋四件套、测试。
2. **MVP**：云端控制面 + 本地 worker + 知识注入（OpenAlex）+ KGTE（`refine` `inject` `transplant` 三个算子 + J-PUCT + Jev 预判与校准）+ 3 个 Skill。详见 `02-MVP方案-硬盘.md`。
3. **伐谋对照**：用同一个基准包在伐谋上跑相同轮次；双方最优解在私有测试集上统一裁决。
4. **补全**：`crossover` `diversify` `simplify` 三个算子，诊断，报告，session 导出，剩余 4 个 Skill。
5. **泛化**：内存（SmartMem）数据适配器；光放大器用「器材在环」worker 迁移验证。
6. **比赛交付**：technical-design.md、test-report.md、sessions、tag。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| 候选代码作弊（读标签、未来信息） | 临时副本隔离、静态规则、私有测试集复评、诊断复现 |
| 验证集过拟合 | F1 取 bootstrap 下分位；报告 val/test 间隙；私有集只用于裁决 |
| Token 成本失控 | 子树记忆按需摘要；经验代替整段代码传播；LLM Gateway 缓存与预算熔断 |
| Jev 判断在本任务上不准 | 在线校准与信任度 τ（不准时自动退化为 UCT）；10% 随机复核；评判问题自动修订并离线回放验证 |
| Jev 服务不可用或无 Key | `JudgeClient` 接口不变，退化为千问多次采样估计分布（慢、贵），或直接使用均匀先验 |
| 文献检索质量差或大模型编造 | 元数据只取自 API；卡片必须附原文证据；实测效用修正先验 |
| 本地 worker 被回收或掉线 | 租约与重新入队；心跳超时暂停调度；推荐 tmux/nohup 手动启动 |
