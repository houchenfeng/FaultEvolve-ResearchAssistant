## B. 数据集调研

### B.1 Codabench 3586：WWW 2025 SmartMem 内存故障预测【已核实，来源为 `https://www.codabench.org/api/competitions/3586/`，用 curl 获取；WebFetch 返回的是无关的垃圾页面】
- **任务**：预测每条 DIMM（按 SN）是否会在未来发生不可纠正错误（UE），属于二分类，但采用**流式/事件式**协议。在时刻 t 只能用 t 之前的日志；lead time 15 分钟，预测窗口 7 天；提交 `sn_name, prediction_timestamp, serial_number_type`，同一个 SN 允许多次预测。
- **数据**：mcelog 错误日志，23 列（cpu/channel/dimm/rank/device/bank/row/column、retryrderrlog、burst_info、error_type、log_time、厂商/型号/PN/容量/频率/McaBank/memory_type/region 等）+ `failure_ticket.csv`（serial_number, failure_time, serial_number_type A/B）。Stage1 feather 解压约 **40GB**，CSV 解压约 **130GB**；另有 Kaggle 特征集 `smartmem/smartmem-features`（页面 HTTP 200，大小**未核实**）；Phase 2 原始数据放在 USTC 网盘。起步代码在 GitHub `hwcloud-RAS/SmartHW/competition_starterkit`（baseline.py 等）。
- **指标**：F1（Codabench 排行榜 key = `f1_score`）。Phase 1 晋级线 F1 > 0.207。获奖队 Phase 2 的 Codabench F1 为 0.299–0.618，但**复现 F1 只有 0.191–0.372**（winners 页），说明过拟合/泄漏风险很大。
- **许可/访问**：需要在 Codabench 注册（auto-approve = True）；数据条款写 CC BY-NC-SA 4.0（链接实际指向 BY-NC），**仅限非商业用途，禁止再分发**，并且"比赛期间禁止使用组织方以外的数据"。Phase 2 已于 2026-03-07 结束，**排行榜不能再提交**，只能用训练数据自建时间外推的验证集。SharePoint 下载链接现在是否可用**未核实**。
- **与 TaskAdapter 的契合度**：接口层可以接入（`evaluate(code) → combined_score`），但需要**自己写** `evaluator.py`（复现 15min/7d 事件式 F1）和 `prepare_data.py`（数据量需下采样到能在 600s 内跑完）。与 HDD 的"每盘一个 cutoff 快照"不同：它是**不规则事件流 + 多次预测时间戳**，候选程序的 CLI 契约需要改成输出多行时间戳。工作量大（下载 40GB+、写评估器）。**建议作为泛化阶段的第 2 个任务，而不是第 1 个。**

## C. 高漏告率诊断与进化系统层面的杠杆

### C.1 评估器事实【已核实，`benchmark/hdd_mvp/evaluator.py` 与 `data/meta.json`】
- `ROS = 100 × (0.5·F1_p10 + 0.3·AUPRC + 0.2·R@FAR) × time_factor`，`time_factor = min(1, 600/运行秒数)`，900s 硬超时。
- **0.2% 的 FAR 预算只作用于 R@FAR 这一项**（用 `score` 排序计算），**对 `alarm` 没有任何硬约束**。`alarm` 只通过加权 F1 与 bootstrap F1_p10 影响得分。
- F1_p10：正负分层 bootstrap 200 次，取加权 F1 的 10% 分位数，惩罚阈值不稳定的方案。
- 负样本权重：val 为 10.07（train 9.86，test 10.32）；val 有 756 正 / 29,998 负。

### C.2 推算【推算】
- 机队口径下 val 正例率 ≈ 756 / (756 + 29,998×10.07) ≈ **0.25%**。
- 当前最优（PR #2）FPR 0.30% → 加权 FP ≈ 906（约 90 个抽样负盘被告警）；TP ≈ 0.439×756 ≈ 332；P = 332/(332+906) ≈ **0.268**，与报告值一致。**所以每多告警 1 个负盘，就相当于约 10 个 FP。**
- 如果精度保持 0.268、召回提到 0.60，FPR 会升到约 0.41%，F1 ≈ 0.371。**单纯下调阈值换召回，F1 提升有限，因为精度会同步下降**。召回和精度要同时提高，只能靠 **top 0.3% 区间的排序质量**（即 AUPRC / R@FAR 本身）。
- 边际收益：F1_p10 +0.01 → ROS +0.5；AUPRC +0.01 → +0.3；R@FAR +0.01 → +0.2。排序质量会同时推动三项。
- 由 PR #2 数字反推：50·F1_p10 + 20·R@FAR ≈ 32.57 − 30×0.319 = 23.0（假设 time_factor = 1，**未核实**）。
- PR #1 最优（ROS 34.96，R 0.558，F1 0.366）**高于** PR #2 最优（32.57）。可能是运行间方差大，或 PR #2 改变了搜索动态，**原因未核实**。这说明单次运行的 best 不可靠，节点价值需要考虑噪声（与 PR #5 相关）。
- 结构性上限（参考）：Backblaze 2016 年的博客称 23.3% 的故障盘在其记录的 5 个 SMART 指标上**没有任何预警**（https://www.backblaze.com/blog/what-smart-stats-indicate-hard-drive-failures/ ，【已核实原文】；但机队与年代不同，用于本数据只是**参考**）。另外，正样本的 cutoff = 故障日 − k（k 在 1..7 均匀分布），k 越大信号越弱（来自 PR #3 knowledge/README 对 prepare_data 的描述）。

### C.3 进化系统当前的缺口【已核实，读自代码】
1. **错例画像始终为空**：`_run_one_iteration()` 用 `metric.get("analysis", {})` 作为错例画像，但 HDD 评估器不输出 `analysis` 字段，`FamouAdapter.evaluate()` 也不生成。可 refine 指令却要求"针对错例画像中最主要的误告或漏告来源……漏告率较高的厂商或型号"，**LLM 被要求做它拿不到数据的事**。
2. **节点价值是单一标量**：`UCTSelector._compute_q()` 只看 `combined_score`（subtree max-backup），不区分这次提升是来自排序（AUPRC/R@FAR）还是来自一次偶然的阈值。
3. **只有 REFINE 一个算子**：`select_operator()` 固定返回 REFINE；`OperatorType.INJECT/TRANSPLANT` 和 `get_operator_thompson_sample()` 都是桩；没有交叉/集成算子。
4. **反思不看 FN/FP**：`LayeredReflector` 只基于 delta 与代码 diff，不知道哪些盘被漏掉。
