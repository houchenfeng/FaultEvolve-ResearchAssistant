## 1. 判分细则：官方页面原文已核录，请确认我们照它实现的是不是同一把尺子

**先更正上一版的一句话**：上一版这里写"细则尚未公布、两条全靠自定"。本地有一份逐字核录
（`memory-predict/knowledge/官方判分规则_核录0926.md` §3，2026-09-26 浏览器实读 Codabench 3586
公告页，非转述），里面**确实写了**：一台机器（SN）只计一次、命中必须落在
`[真实故障时刻 − 7 天, − 15 分钟]` 内、precision 分母是"被预测的 SN 数（去重）"、
recall 分母是"工单里的 SN 总数"。我们已把这条设为默认 `--duplicate-alarm-rule sn-in-window`，
另两条留作上下界：`each-alarm`（`SMARTMEM_PHASE2_REQUIREMENTS.md` §5.1 要求的本地兜底协议）、
`once-per-unit`（只看点名、不看时刻）。

**为什么这条从"请给细则"降为"请确认"**（`已实测`，200 单元切片，提交=只预测 `label=1` 的行，
不含任何模型，所以是这份尺子的上界）：

| 细则 | dev F1 | val F1 | dev 预测数 / 告警数 |
| --- | --- | --- | --- |
| `sn-in-window`（默认，照页面原文） | **1.0** | **1.0** | 37 / 37（val 26 / 26） |
| `each-alarm`（一条告警一个事件，窗内贪心配对） | 0.08496 | 0.082019 | 834 / 37 |
| `once-per-unit`（点名即算，不看时刻） | 1.0 | 1.0 | 37 / 37 |

**要确认的就两点**：

1. **`serial_number_type` 报错是否作废该命中。** 提交格式要求带这一列，判分说明里没有它。
   我们的侧表已把 200 单元的类型全部定出来（`已实测`：与工单交叉校验 140 个有工单单元全部命中、
   类型冲突 0 处、unresolved 0），
   但如果判分根本不看这列，我们就不该把它当约束。
2. **是否只统计"预测时刻落在考卷日历窗内"的记录**（核录 §3 说 6/1~7/31）。本仓按 `split_key`
   切片打分，没有这一层过滤；补它只需要在 `_report` 前加一道日期闸门，但**会改分数**，所以要先问。

**顺带一条如果你们问到就更好**：有没有官方可执行 scorer（源码或参考输出）。页面原文 ≠ 可执行 scorer，
拿到才能把 `metric_spec_status: provisional` 摘掉；另外有没有 **top-1% / 告警预算 / 阈值**这类
precision 侧约束 —— 没有的话这把尺子对"多报"几乎无惩罚，而"跟着标签报"就能拿满分。
A/B 两队列的汇总已按原文取"整个 SN 集合算一次"（`--queue-aggregation sum`），`mean-of-f1` 只作敏感性
检验；本切片上两者给同一个数（告警全落在队列 A，队列 B 的 alarms=0）。

## 2. 验收方言：交产物还是交原始 mcelog 列

**现在的默认**：只产出本仓的样本表 + 侧表（44 列，含 `unit_id` / `prediction_time` / `split_key`）。

**为什么**：官方预计算特征表的列名与顺序（`FrequencyMHz`、`MaxSpeedMHz`、`marked_rate` 族）我们
没有一份可对照的样例，反向转换器不存在、列顺序会在重建时丢掉，所以即便导出也只能证"值相等"、
证不了"字节相等"。据此决定把 `--emit-dialect` 从本轮砍掉，记在下轮。

**要的答案**：验收看哪张表、列名以谁为准、是否要求逐字节复现官方特征文件。
