# SmartMem 知识包 - 专家说明（expert.md）

这份文件写给**人**读。机器读的是同目录下的 `cards.jsonl`，引用出处记在 `sources.yaml`，
本文件只回答三件事：这些卡片是在什么证据上写出来的、哪些判断还**不能**算知识、
以及要把这个数据包交给下一位作者时他必须知道的约束。

## 1. 卡片与本文的分工

| 制品 | 读者 | 内容标准 |
|---|---|---|
| `cards.jsonl` | 引擎（prompt 注入） | 每条 claim 必须有 `source_ids`、适用条件、预期影响、风险 |
| `sources.yaml` | 复核者 | 只允许登记**真实读到过**的文献或页面，附 URL、读取方式、读取日期 |
| `expert.md`（本文件） | 组内成员与评委 | 背景、边界、未定问题；不承担可注入性 |

三者的一致性由 `benchmark/smartmem/knowledge_check.py` 校验，运行方式见第 6 节。
卡片里的每一条都能在 `sources.yaml` 中找到出处；本文件允许写"还没有出处"的内容，
但必须明确标记为猜测。

## 2. 证据是怎么来的（2026-10-03 的核验记录）

写入卡片前实际完成的外部动作，只有这四类：

1. **赛题与评测口径**：赛事主页 + 仓库 README + CodaBench 平台记录。据此固定
   lead 15 分钟、预测窗 7 天、以 F 分（带 beta 旋钮）判分、观测窗与打标方式由参赛者自定。
2. **官方 starter kit**：README 与 `baseline.py` 逐行读。特征族（temporal / spatial / parity）、
   窗口取值、缺失值填 `-1`、正负样本的取法、LightGBM、提交列，全部来自这份实现而不是转述。
3. **DRAM/ECC 论文**：arXiv API 取标题、作者、日期与摘要原文，共五篇
   （2021 mcelog 挖掘、2022 first-CE 长程性质、2023 error-bit 时空相关、
   2024 跨 CPU 架构、2025 M2-MFP 多层二值矩阵）。
4. **组内既有尝试**：`docs/runs/smartmem-existing-attempt-analysis.md` 是本仓的只读分析记录，
   以匿名 run id 登记，标记 `evidence: user_run`，**不含私有路径与真实序列号**。

没有做过的动作就不写进 `sources.yaml`：往届获奖方案的代码没拿到（榜单已关闭），
所以卡片中凡是"往届怎么做"的说法一律没有登记出处，也就没有进卡。

## 3. 为什么知识注入要单独占一个阶段

数据适配解决的是"能不能跑"，知识解决的是"跑出来的东西是不是一开始就走错方向"。
本任务最容易犯的四类错误都是**协议类**错误，不是模型类错误：以告警为锚点造样本、
把未随访的区间当确认负例、在评估集上扫阈值、随机按单元划分却宣称能预测下个月。
这四条在旧尝试里都出现过，而且当时并没有被当作错误 - 它们只在换了一把尺子之后才暴露。
所以卡片的 `category` 里 `pitfalls / labeling / thresholding / evaluation` 合计占比接近一半，
这是有意的，不是主题分布失衡。

## 4. 数值的可读性约定

1. 卡片的 `expected_effect` 只允许写**方向与量级**，且必须说清量级的口径
   （哪个数据集、哪把尺子）。没有可引用口径时写"需在本地测"，不编造数字。
2. 论文里的百分比（例如 error-bit 特征、平台感知建模带来的 F1 提升）是**该文实验**的结果，
   不是本数据集的预期；卡片保留原文数字并标注出处，禁止搬运成"我们也能拿到"。
3. 旧尝试的绝对分数只在一张卡里以"历史参考"身份出现，且卡片本身写明它测的是另一套协议。
   新协议的第一个可用分数出来之前，任何"提升"表述都不成立。
4. 判分口径未确认前（见第 5 节），任何 SN 级分数都要同时说明命中窗的取法，
   否则两个数字不可比。

## 5. 开放问题：已实测的部分与仍需等人的部分

本地镜像能测的在 2026-10-03 已经全部测过一遍。标 **待确认** 的三条会改变卡片的适用条件，
拿到答复之前**不升为 verified**；标 **已实测** 的以本地镜像的数字为准，不必再问人。

1. **待确认** 时间边界口径：官方特征的时刻是 UTC 还是本地时区，是否影响告警时刻的减法；
2. **口径已裁定（2026-10-04）** `outcome_observed_until`（每台机器真实随访到何时）：逐台真值拿不到，
   本地按"全局随访前沿"实现——取数据里最晚的观测时刻作为截止。**2026-10-04 实测说明这条口径有代价**：
   200 单元切片里事件前沿到 2024-07-31，工单只覆盖到 2024-05-31（相差 61 天），按现口径产出的
   19 540 行样本里有 1 866 行（9.5%）锚点落在工单覆盖之外、全部 `label=0`，是"未随访"而不是
   "确认无故障"，`val` 分区因此一个正样本都没有。合适的口径是 `min(事件前沿, 工单覆盖终点)`，
   机制本身已正确实现，只差这个入参；因为与 V1-00 输入证据里记录的候选（取 2024-05-31 当日结束）
   冲突，所以当时**没有擅自改**。2026-10-04 组内裁定并按这条落地：`split-v2.yaml` 取工单覆盖终点
   `2024-05-31T01:13:37+00:00`（同时把 `val_until` 收进覆盖区，硬约束 `val_until + 7d00:15 ≤ 前沿`
   由 CLI 守住），两条路径复跑后样本 17 531 行、消失的 2 009 行全是负例、正样本 4 613 未少，`val`
   第一次有正样本（608 行 / 26 个单元），运行载荷的 `coverage.rows_beyond_coverage` 归 0。
   注意这批行是**不再被生成**而不是记成 `censored`——`val_until` 一起挪进了覆盖区间，所以现存每个
   负例都是观察到的；官方若给出逐台随访终点，只改入参不动机制；
3. **已实测** 目录与 ticket 的文件名与"文件名到单元"的映射：本地镜像是 `type_A` / `type_B` 两个队列
   目录（共 62 224 个 `sn_<编号>.feather`）加一份 `ticket.csv`，列为 `sn_name` / `alarm_time` /
   `sn_type`；镜像里没有 `train/` 目录，`failure_ticket.csv` 是同一份工单的另一份拷贝。适配器把
   `train` / `type_A` / `type_B` 三个队列名都认，文件名到单元的映射有测试钉住；
4. **本地已交付（2026-10-04）** 无告警单元的 `serial_number_type`：`build_unit_type_table()` 产出
   `units/serial_type` 分区（列 `unit_id` / `serial_number_type` / `source`），目录声明优先、工单只做
   交叉校验、两者不一致退 1，谁都没声明的单元记 `unresolved` 且**不猜**；这张表还进 `config_hash`
   （`unit_type_fingerprint`），所以换队列目录不能续跑。200 单元切片上 200 行全部由目录声明、与
   140 条工单零冲突，本地不再缺这一列。**待确认的只剩官方口径**：静默单元的类型是否也按目录给；
5. **页面原文已核录、评分源码未到手** 官方评分实现：本地核录（`官方判分规则_核录0926.md` §3，
   逐字读 Codabench 3586 公告页）写的是**一台机器只计一次 + 命中必须落在 `[告警−7天, 告警−15分钟]`
   内**，precision 分母是"被预测的 SN 数（去重）"、recall 分母是"工单里的 SN 总数"。本地 evaluator
   已按它设默认 `sn-in-window`，另留 `each-alarm`（§5.1 兜底协议）与 `once-per-unit` 作上下界；
   200 单元切片实测"只预测 `label=1` 行"的 oracle：`sn-in-window` F1=1.0、`each-alarm` 0.082、
   `once-per-unit` 1.0。⇒ 拉开一个量级的是**去重与否**，不是时刻；仍待确认的是组委会源码是否真的
   这样实现、有没有告警预算/top-1% 这类 precision 侧约束、`serial_number_type` 报错是否作废命中。
   这就是给队长的问题清单第一条；
6. **已实测（样本）** `error_type` 的取值域：镜像的 460 个单元文件样本（624 万余行事件，镜像共
   62 224 个单元文件）只出现 `CE.READ`、`CE.SCRUB`、`CE` 三种写法，样本事件流里没有 UE——UE 只
   出现在工单里。因此 `--error-types` 的默认值就是这三种拼写，比较区分大小写，声明了一个都盖不住的
   取值域会被 `--profile-only` 拒绝；样本不是全量，所以这个默认值随时可被该检查当场证伪；
7. **已实测（本地）** 运行环境包含 pyarrow，`--format feather` 可用；服务器侧仍需当场确认一次；
8. **本仓自定** 分块规模与每分区单元数（当前默认 64 不是官方约束）；
9. **已实测（200 单元真实切片）** 两条读取路径等值：同一批 200 个真实单元，raw 直读与
   `--from-sorted` 吃排序树各跑一遍，`config_hash` 相同、审计数字相同、19 540 行样本按
   `sample_id` 对齐后**数值差异 0 处**，只有 **9 612 格**是同值两种写法（`4000.0` 对 `4000`），
   且**只出现在 `FrequencyMHz`（1 015 格）与 `MaxSpeedMHz`（8 597 格）**——我先前写过"14 612 格、
   含两个 marked_rate 列"，10-04 用两种独立对齐方式复核后撤回那个数，速率列一格不差。
   成因是存储 dtype：镜像里部分单元把频率存成 float64（带空洞）、部分存成 int64，读进特征列后
   由分区内混合标量推断出 float64，而排序树把同一个数当文本读回、推断出整数。修法已落地：
   `FEATURE_MANIFEST` 给每个特征声明可应用的 dtype，`canonicalize_feature_types` 在写出前统一渲染，
   整数值列走可空整型（`4000`），带小数或非数字的值**当场拒绝**而不是悄悄 coerce 成空格。
   另有一条**我自己列错后撤回**的口子：`config_hash` 不含事件来源
   不是缺陷，`_config_payload` 的文档写明 `--from-sorted` 是**有意不进哈希**（复跑同一棵与原始文件一致的
   树只是到达同样字节的另一条路，两次该记同一个 hash），来源本身记在 payload 与 manifest 的 `events`
   字段里。今天实测真正推翻的是这条设计的**前提**——两条路并不到达同样字节。所以补一条契约测试：
   两条路径必须给出同一 `config_hash` **且**同一分区 sha256。
   **修完复跑已达成**：同一批 200 单元重写进 `out-raw2` / `out-sorted2`，`config_hash` 同为
   `fd5a113d…`，51 个分区的 sha256 **逐分区相同**，19 540 行按 `sample_id` 对齐后**文本差异 0 格**
   （修前 9 612）；写出字节里所有带 `.0` 的格子都来自声明 `float64` 的列。
   顺带挖出一条**还没修**的口子：渲染策略不进 `config_hash`（`_config_payload` 的 17 项里没有
   描述特征渲染的项），所以拿改前产出的 out 目录续跑，旧写法的分区会被当成已完成跳过，新旧两种
   口径挂在同一个 hash 下——本轮实测本身就是证据：修前修后 `config_hash` 一字未变。下一轮把
   渲染版本号进 payload，并补一条"旧口径目录不许续跑"的测试。
   详见 `docs/runs/smartmem-v1-dev-log.md` 的 V1-10 一节。

只能等外部答复的剩第 1、4、5 条。第 2 条（前沿口径）与第 9 条（两路径等值）都已在本仓内部解决：
前者 2026-10-04 组内裁定取工单覆盖终点，后者已修并复跑核验；第 9 条末尾那条"渲染版本不进
`config_hash`"是新挖出的待修，不需要问人。

## 6. 校验与复现

```text
python -m pytest tests/test_smartmem_knowledge.py -q
python -m benchmark.smartmem.knowledge_check
```

第二条命令打印卡片数、来源数与类别/证据分布；有任何一条规则不满足就逐行打印并以 1 退出。
新增卡片时**必须**同时：给 `source_ids` 找到 `sources.yaml` 里的条目，
填满 `rationale / applicability / expected_effect / risk / impl_hint`，
并确认 `id` 保持 `SM-` 命名空间。
